# FSC 電子支付統計網站：系統架構與維護手冊

最後更新：2026-08-18

本文件說明 `fsc_web` 專案目前的正式架構、資料來源、更新方式、部署流程、權限設定與故障排除。目的在於讓維護者不需要依賴先前對話，也能完成每月資料更新與網站維護。

## 1. 系統現況

| 項目 | 目前設定 |
|---|---|
| GitHub repository | `bruce912/fsc_web` |
| 預設分支 | `main` |
| Cloudflare Pages 專案 | `fsc-web` |
| 正式網站 | <https://fsc-web.brucelab.org> |
| Pages 原始網址 | <https://fsc-web.pages.dev> |
| 本機預覽 | <http://127.0.0.1:8001> |
| 主要資料庫 | `FSCWEB/fsc_ebank.db`（SQLite） |
| 靜態網站目錄 | `FSCWEB/static_site/` |
| 全業者統計最新資料 | 民國 115 年 06 月 |
| ebank 申報資料最新月份 | 民國 115 年 07 月（各報表月份可能不同） |

正式環境採用「靜態網站」架構。Cloudflare Pages 只提供已產生的 HTML、JavaScript、CSS 與 JSON，不會在訪客瀏覽時啟動 Flask、Python 或 SQLite。

## 3. 主要元件與責任

### 3.1 本機 Flask 版本

`web_app.py` 是原始完整應用，負責從 SQLite 提供 API、資料匯入、查詢、匯出及本機功能。它仍可供開發、測試與資料管理使用，但不是正式網站的執行環境。

```bash
cd FSCWEB
python3 -m pip install -r requirements.txt
python3 web_app.py
```

### 3.2 靜態網站版本

`export_static_site.py` 使用 Flask 測試客戶端與 SQLite，把所有查詢資料整理成 `static_site/data/app-data.json`，並複製前端資源至 `static_site/`。

靜態版保留：

- 儀表板與資料表瀏覽
- 月份比較與趨勢圖
- 全業者統計
- 月票統計
- 文件瀏覽
- 瀏覽器端 CSV 匯出

靜態版不提供：

- 在正式網站直接修改 SQLite
- 網頁端執行 Python 更新
- 本機 Ollama 聊天服務
- 需要伺服器寫入權限的資料匯入

### 3.3 GitHub Actions

`.github/workflows/update-industry-stats.yml` 是公開揭露資料的自動維護工作。GitHub Actions 相當於臨時啟動的更新電腦：安裝 Python、下載資料、更新 SQLite、重建靜態網站、提交 GitHub，最後部署 Cloudflare Pages。

排程設定：

- 每月 12 日 10:15（台北時間）自動檢查
- 每月 19 日 10:15（台北時間）再次檢查
- 可從 GitHub Actions 手動執行
- Codex 另於每月 15 日 09:00（台北時間）提醒維護者檢查更新

如果金管會沒有新月份，Action 會正常結束，並跳過重建、提交與部署。步驟顯示 `Skipped` 屬正常結果。

### 3.4 Cloudflare Pages

Cloudflare Pages 負責正式網站託管、HTTPS、自訂網域及 CDN。部署來源為 `FSCWEB/static_site/`，Pages 專案名稱為 `fsc-web`。

`brucelab.org` 根網域沒有綁定本專案；本專案只使用 `fsc-web.brucelab.org`。

## 4. 資料來源

### 4.1 全業者統計（可完全自動化）

來源是銀行局「電子支付帳戶重要業務資訊揭露」公開頁面。每月提供 ZIP，內含 Excel。此來源不需帳號密碼，因此 GitHub Actions 可直接更新。

相關程式：

| 檔案 | 用途 |
|---|---|
| `update_industry_stats.py` | 找出資料庫最新月份之後的新 ZIP、下載、驗證與匯入 |
| `import_disclosure_zip.py` | 解析 ZIP 內 Excel，寫入 SQLite 的「全業者統計」表 |
| `電子支付機構_全業者統計.csv` | 可重建資料庫的歷史來源與人工查核檔 |

安全機制：

- 下載內容必須是有效 ZIP
- ZIP 必須能解析出資料
- 最新月份若失敗，整次更新會停止，不發布舊資料
- 同月份匯入採先刪後插，避免重複
- 只處理資料庫最新月份之後的資料，避免舊失效連結阻塞每月工作

### 4.2 ebank 27 項申報報表（需要人工登入）

`ebank.banking.gov.tw` 需要人工登入及驗證，不能把帳號密碼放入 GitHub Actions。因此這一部分仍採人工啟動、程式自動抓取。

相關程式：

| 檔案 | 用途 |
|---|---|
| `ebank_monthly_updater.py` | Playwright 自動巡覽 27 項報表，登入由維護者完成 |
| `ebank_monthly_updater.js` | 使用已登入瀏覽器 Session 的備用版本 |
| `merge_updates.py` | 合併增量 JSON 與歷史 JSON |
| `build_database.py` | 從合併資料重建 SQLite |

### 4.3 其他資料

- `行政院月票交易統計報表(for+金管會).xlsx`：月票統計來源，現階段人工更新。
- `資料庫欄位說明.md`：資料表與欄位定義。
- `專案功能文件.md`：原始完整功能與資料處理說明。

## 5. 每月標準維護流程

### 5.1 每月 15 日例行檢查

1. 開啟 <https://github.com/bruce912/fsc_web/actions/workflows/update-industry-stats.yml>。
2. 查看本月 12 日的執行結果。
3. 若尚未執行或想立即檢查，按 `Run workflow`。
4. Branch 選 `main`。
5. 再按綠色 `Run workflow`。
6. 等待 `Update FSC industry statistics` 顯示綠色 `Success`。
7. 若發現新月份，確認下列步驟均成功：
   - `Download and import new FSC disclosure data`
   - `Rebuild static site`
   - `Commit updated data`
   - `Deploy to Cloudflare Pages`
8. 開啟 <https://fsc-web.brucelab.org>，進入「全業者統計」，確認最新資料月份與機構資料可顯示。

### 5.2 沒有新資料時

以下狀態是正常的：

- Workflow 結果為 `Success`
- 下載與比對成功
- `Rebuild static site` 顯示 `Skipped`
- `Commit updated data` 顯示 `Skipped`
- `Deploy to Cloudflare Pages` 顯示 `Skipped`

代表金管會尚未發布新月份，而非更新失敗。

## 6. 手動更新方式

### 6.1 手動更新全業者統計

```bash
cd FSCWEB

# 只檢查金管會是否有新月份
python3 update_industry_stats.py --dry-run

# 下載並匯入新月份
python3 update_industry_stats.py

# 重新產生靜態網站
python3 export_static_site.py

# 本機預覽，使用 8001 避免與其他程式衝突
python3 -m http.server 8001 --directory static_site
```

完成後應確認：

```bash
sqlite3 fsc_ebank.db \
  'SELECT yr,mn,COUNT(*) FROM "全業者統計" GROUP BY yr,mn ORDER BY yr DESC,mn DESC LIMIT 5;'
```

### 6.2 手動更新 ebank 27 項報表

預設執行增量更新，不要加 `--reset`：

```bash
cd FSCWEB
python3 ebank_monthly_updater.py
```

操作時：

1. 等瀏覽器開啟 ebank。
2. 人工完成登入與驗證。
3. 回到終端機按 Enter。
4. 等待 27 項報表完成，不要關閉瀏覽器。
5. 確認錯誤項目為 0，或逐一處理失敗報表。
6. 合併與建庫：

```bash
python3 merge_updates.py
python3 build_database.py
python3 export_static_site.py
```

重要：`build_database.py` 會重建 SQLite。執行前應確認 `電子支付機構_全業者統計.csv` 已包含最新全業者資料，避免重建後月份倒退。

## 7. GitHub 與部署操作

### 7.1 需要提交的更新檔案

資料更新後通常包含：

- `FSCWEB/fsc_ebank.db`
- `FSCWEB/電子支付機構_全業者統計.csv`
- `FSCWEB/static_site/data/app-data.json`
- 其他真正有變化的 JSON 或來源檔

不要提交：

- `.DS_Store`
- `.wrangler/`
- Token、密碼或瀏覽器 Session
- 臨時下載 ZIP（除非刻意要保存原始檔）

### 7.2 GitHub Actions Secrets

Repository Settings → Secrets and variables → Actions 必須存在：

| Secret 名稱 | 用途 |
|---|---|
| `CLOUDFLARE_API_TOKEN` | Cloudflare Pages 部署授權，權限為 Account / Cloudflare Pages / Edit |
| `CLOUDFLARE_ACCOUNT_ID` | 指定 Cloudflare 帳戶 |

只檢查 Secret 名稱是否存在；GitHub 不會再次顯示 Secret 內容。Token 不得寫進 repository。

### 7.3 手動 Cloudflare 部署

自動部署故障時，可在已登入 Wrangler 的環境執行：

```bash
npx wrangler pages deploy FSCWEB/static_site \
  --project-name=fsc-web \
  --branch=feat/static-site-export
```

部署完成後同時驗證：

- <https://fsc-web.brucelab.org>
- <https://fsc-web.brucelab.org/data/app-data.json>
- Cloudflare Pages 專案 `fsc-web` 最新部署狀態為 Success

## 8. 驗證清單

每次資料更新或部署後至少檢查：

- [ ] GitHub Actions 為綠色 `Success`
- [ ] SQLite 最新月份正確
- [ ] 新月份筆數不是 0
- [ ] `static_site/data/app-data.json` 已重新產生
- [ ] 正式網站 HTTP 可正常開啟
- [ ] 「全業者統計」顯示正確最新月份
- [ ] 其他主要儀表板可載入
- [ ] 瀏覽器 Console 沒有資料載入錯誤
- [ ] `.DS_Store`、`.wrangler/` 與憑證未被提交

## 9. 常見問題與處理

### Action 成功，但部署步驟被跳過

先確認是否真的有新月份。沒有資料變動時，重建、提交與部署會刻意跳過。

### Action 失敗：找不到 ZIP

可能原因：

- 金管會調整頁面或連結格式
- 金管會網站暫時無法連線
- 新檔案不是有效 ZIP

處理方式：先在瀏覽器確認公開揭露頁面能下載 ZIP，再檢查 `DISCLOSURE_URL` 與 `disclosure_links()`。

### Action 失敗：Excel 無法解析

金管會可能修改工作表、月份位置或欄位排列。先下載該月 ZIP，檢查 Excel 前六列及資料欄位，再調整 `import_disclosure_zip.py`。修改後應先在資料庫副本測試。

### Cloudflare 部署失敗

依序檢查：

1. GitHub Secrets 名稱是否正確。
2. Token 是否過期或被撤銷。
3. Token 是否有 `Cloudflare Pages: Edit`。
4. Pages 專案名稱是否仍為 `fsc-web`。
5. Cloudflare 帳戶是否正確。

### 網站仍顯示舊月份

依序確認：

1. SQLite 是否已有新月份。
2. `export_static_site.py` 是否成功執行。
3. `app-data.json` 是否包含新月份。
4. Cloudflare 最新部署是否成功。
5. 使用無痕視窗或強制重新整理，排除瀏覽器快取。

### ebank 爬蟲失敗

常見原因包括登入 Session 失效、iframe 變動、DataTable 載入逾時及表格結構更新。先參考 `專案功能文件.md` 與 FSC updater troubleshooting，再修改擷取邏輯。

## 10. 復原策略

### 資料庫更新錯誤

1. 不要部署錯誤版本。
2. 從 GitHub 前一個正常 commit 取回 `fsc_ebank.db`。
3. 重新執行匯入與驗證。
4. 重新產生 `static_site/`。
5. 確認資料後再部署。

### 已部署錯誤網站

可在 Cloudflare Pages 的 Deployments 選擇前一個成功部署重新發布，或在 GitHub 回復正確資料後重新執行部署。

### Token 外洩

1. 立即到 Cloudflare API Tokens 撤銷該 Token。
2. 建立新的最小權限 Token。
3. 更新 GitHub 的 `CLOUDFLARE_API_TOKEN` Secret。
4. 檢查 GitHub 與 Cloudflare 操作紀錄。

## 11. 修改架構時的原則

- 正式網站繼續以靜態檔案為發布單位。
- 不要讓瀏覽器取得可修改 GitHub 或 Cloudflare 的憑證。
- 公開資料可自動化；需登入資料保留人工驗證。
- 新資料必須先驗證，再提交與部署。
- 資料庫、歷史來源與靜態輸出需保持一致。
- 任何自動化都必須在無新資料時保持冪等，不製造無意義提交。
- 權限採最小化原則，Token 只授權需要的 Pages 專案操作。
